# Plan — the rest of v1.0

The first public release. Everything left between #44 (now merged) and tagging
`v1.0.0`. The high-level order is fixed in `docs/ROADMAP.md`; this document is
the in-depth execution plan behind it: what each ticket changes, how it is
verified, who does it, and in what order they land so nothing collides.

## Non-negotiables

- `./test.sh` passes before any push. New behaviour has a test.
- No personal information and no game assets in the repository, releases, or
  anything written on GitHub (`AGENTS.md`). `PrivacyTest` is never weakened.
- Tests use invented data. The owner's own export, ROM, saves and artwork live
  in gitignored local folders and are never committed or referenced by path.

## How work is split

- **High-touch (inline, TDD, review before merge):** anything that changes data
  integrity or is irreversible — the music engine (#46), vault management (#41),
  activity deletion (#38), the history decision (#49), the cleanup (#52), the
  installers (#56) and the release itself (#53).
- **Agents (self-contained, reviewed before merge):** the UI and doc work —
  logo (#57), Notion import (#48), polish (#47), license (#50), README (#51).

Every branch is `claude/<name>`; each merges to `main` through a PR whose body
closes its issue.

## The tickets

### #46 — the game's own songs as study music  *(high-touch)*

Replace the WAV/AIFF import (`assets/MusicLibrary.java`, `ui/MusicPlayer.java`)
with Emerald's soundtrack, read from the player's own ROM and synthesised in
Java. The M4A "Sappy" engine in miniature: the ROM's song table (songs, voice
groups, tracks), DirectSound voices (square, wave, noise, and the compressed
PCM samples), ADSR envelopes, and the reverb. A sequencer turns a track into
frames fed to a `SourceDataLine`, so calm route and town themes play while the
timer runs.

- **Scope.** Parse the song table from the ROM at runtime; implement the
  sequencer and voices; a Settings section to pick tracks, skip and set volume;
  pause while the game itself is running; nothing written to disk or committed.
  Without a ROM the music settings say what to add.
- **Files.** New `dev.yoru.game.music.*` (song table, sequencer, voices,
  envelopes); `assets/MusicLibrary` becomes the ROM-sourced library;
  `ui/MusicPlayer` gains the sequencer path; Settings page.
- **Tests.** The engine is unit-tested against hand-built M4A structures
  (invented note data, envelopes, a voice of each kind). The ROM parser is
  tested against a synthetic song-table header. Where the existing encounter and
  learnset tests gate on a real ROM, music does the same; no song data is
  committed. Keep the existing format/path-escape checks.
- **Done.** A playlist plays synthesised routes/towns while the timer runs,
  pauses in-game, and the suite is green with no committed song data.

### #48 — import tasks from a Notion export  *(agent, tight spec)*

Accept Notion's Markdown & CSV export — the zip as downloaded, or the CSV inside
it — and turn it into Yoru tasks in one transaction.

- **Scope.** Auto-map the usual columns (title, status or checkbox, due date,
  class/tag/category) with a preview to adjust before saving; page text becomes
  notes, classes become tags, duplicates are skipped.
- **Files.** New `dev.yoru.import.NotionImport` behind the existing
  `plugins/ImportProvider`; a panel following `ui/TaskPastePanel`; wiring into
  Tasks or Data.
- **Tests.** An invented export with the same shape (never a real one): mapping,
  notes, tags, duplicate skipping, and the one-transaction commit; UI preview.
- **Done.** A Notion export imports to tasks with a mapping preview and no
  partial writes.

### #57 — a new logo and app icon  *(agent)*

The current code-drawn `ui/Logo.java` does not hold up. Redraw it as a night-sky
mark for 夜 — a crisp crescent readable at 16 px, pixel-precise, terminal
typography — on the macOS icon grid as a rounded-square app icon, with light and
dark variants the themes can tint. Export `.icns`, `.ico` and `.png` for the
installers.

- **Files.** `ui/Logo.java`, `ui/Theme.java` (tint), a `tools/` script or build
  step for the exports; `LogoTest` and `LogoPreview` extended.
- **Tests.** `LogoTest` keeps it legible at every size and in every theme.
- **Done.** A mark that reads at 16 px and 1024 px, tinted per theme, exported
  to all three formats.

### #47 — polish: a ricer aesthetic, an Apple-level finish  *(agent, image-reviewed)*

One spacing and type system applied everywhere; consistent controls, focus
states, empty states and wording; themes on well-known ricing palettes; a real
home for the study buddy (a fastfetch-style card with the party's lead as crisp
pixel art, beside its name, level, time studied together and streak); every page
reviewed as a rendered image in every theme; unfinished integrations (plugins,
AI import) hidden until after 1.0.

- **Files.** `ui/Theme.java` and every page under `ui/`.
- **Tests.** `Preview` renders every page in every theme; the change is reviewed
  image-by-image, not by eye in a running app. `ContrastTest` still passes.
- **Done.** Every page reviewed as a rendered image in every theme, buddy card
  present, unfinished integrations hidden.

### #38 — manage study activities  *(high-touch)*

Activities (the Today picker's labels, e.g. "Coding") cannot currently be
renamed or removed. Add management beside the picker. Rename preserves identity
and all recorded time. Removal asks whether to keep the time under "Uncategorized"
or delete it too, shows the affected session count and duration first, preserves
planned blocks and tasks, and refuses while that activity has a running timer.

- **Files.** `domain/Model.java` (activity identity, deletion semantics),
  `application/Tracker.java` (atomic rename/remove with rollback), Today and
  Data pages.
- **Tests.** Rename keeps time; remove-keep and remove-delete both land exactly
  the intended sessions; no unrelated records lost, no reward duplication; the
  running-timer refusal; rollback on failure.
- **Done.** Activities rename and remove safely, with the choice of keeping or
  deleting tracked time, atomically.

### #41 — manage vaults inside Yoru  *(high-touch)*

Vaults stop exposing the filesystem. Create, rename, switch and delete vaults in
the UI; Yoru chooses and manages the storage location, and no screen asks the
user to browse for a vault or save path. Deleting explains what goes (study
data, game progress, saves, backups, reward ledger), requires confirmation, and
a failed deletion leaves the vault recoverable. Switching safely stops the game
first. Existing vaults migrate into managed storage without loss.

- **Files.** `persistence/*` (managed location), `application/Repository.java`
  and `Tracker.java` (create/rename/switch/delete), `ui/VaultLauncher.java` and
  Data page; a migration.
- **Tests.** Create, reopen, switch, delete, failed deletion, and migration, all
  without data loss; personal data stays local and is never packaged.
- **Done.** Vaults are managed entirely in-app, with safe deletion and migration.

### #49 — privacy: the tree is clean; decide history  *(high-touch)*

The tree is already scrubbed (`PrivacyTest`, `AGENTS.md`, denylist). The open
item is how history is cleaned before the visibility change. **Recommendation:
publish a fresh repository from the scrubbed tree** rather than rewriting
history — a rewrite leaves the old commits reachable from forks, reflogs and
caches, and can be done wrong; a fresh repo is provably clean. This is the
owner's call at release time; the plan prepares both a clean-tree export and the
steps, and touches nothing irreversible until then.

- **Done.** A decision is recorded and the release uses a provably-clean tree.

### #50 — license and legal notices  *(agent)*

Unlicense (already in `LICENSE`); a legal notice stating Yoru is not affiliated
with Nintendo, Game Freak or The Pokémon Company, ships no game/BIOS/artwork/
music, and needs the player's own legally obtained copy; credit what Yoru relies
on without bundling (RetroArch, the mGBA libretro core) and pokeemerald as the
save/engine reference.

- **Done.** `LICENSE` and a notice are in place and linked from the README.

### #51 — a README that sells it  *(agent, after #47 and #57)*

Header, one-line pitch, tour of the study → encounters → play loop; screenshots
rendered by the app itself (original artwork only — the app's no-artwork
visuals where the game would appear); quick start, building from source, FAQ,
license and legal notice.

- **Done.** The repository's first screen reads well and uses only original art.

### #52 — codebase cleanup  *(high-touch, last code change)*

Split `ui/YoruApp.java` (~1500 lines) into one class per page behind `Shell`;
remove dead code left by removed features; keep one way to do each thing (file
choosers, save writes, species data); consistent naming and comments; refresh
docs to match. Runs after every feature above so nothing re-splits work.

- **Done.** `YoruApp` is thin; docs match code; the suite is green.

### #56 — installers  *(high-touch)*

`jpackage` builds a `.dmg` with `Yoru.app` (own icon, bundled JRE,
`--enable-native-access`, data under the user's folder), a Windows `.msi` and a
Linux `.deb`, each on its own CI runner. A workflow builds all three on a version
tag and attaches them to the release. Release notes explain the unsigned-macOS
first-open confirmation.

- **Done.** Three installers build in CI and attach to a tagged release.

### #53 — package, verify and tag v1.0.0  *(high-touch)*

A release build that runs anywhere Java runs, with the Game tab explaining what
to add when no game files are present; a clean-account verification (first run,
vault, game setup, Play and Close, delivery, backup and restore); release notes;
tag `v1.0.0`; attach the build (no game files, no artwork).

- **Done.** `v1.0.0` is tagged with a release holding installers and the jar.

## Order and waves

Dependencies: #51 needs #47 and #57; #56 needs #57's exports; #52 must be last
code; #53 last of all. The rest are independent and can parallelise.

1. **Wave 1 (parallel):** #46 *(high-touch, inline)* · #48 *(agent)* · #57 *(agent)*.
2. **Wave 2 (parallel):** #41 *(high-touch, inline)* · #38 *(high-touch)*.
3. **Wave 3:** #47 *(agent, image-reviewed)*.
4. **Wave 4 (parallel):** #50 *(agent)* · #51 *(agent)* · #49 *(decision recorded)*.
5. **Wave 5 (sequential, high-touch):** #52 → #56 → #53.
6. Tick #55 throughout.

Each wave merges before the next starts, so a later wave never re-splits a page
the previous one just touched.
